# Forge 1.20.1 world toolbox — shipping a hand-built valley and changing it without breaking immersion

Research pass for R2 (job "R2"). Scope: five questions about shipping a pre-built world or a pinned-at-worldgen valley, and about additive/gradual world change instead of runtime cut-and-replace. Cross-checked against the 127 mods actually in `server/mods` / `pack/mods` and against this pack's own KubeJS scripts (`valley_core.js`, `valley_checks.js`).

**None of the mods named as candidates below (Serilum Starter Structure, Custom Starter Structure, Spawn Structures, Structure Gel API, Yet Another World Preset / Custom Default World Preset, In Control, FTB Chunks) are currently installed in this pack.** Everything here is "could add," not "already have." What the pack *does* already have that's relevant: Create (Schematicannon, Schematic Table), Waystones, Chunky, FTB Teams/Quests (no FTB Chunks), and a hand-rolled sleep-poll pattern in `valley_checks.js`.

---

## 1. Shipping a hand-built world

### 1a. Carrying a world inside a packwiz-distributed instance

packwiz's `index.toml` format supports exactly the mechanism needed for this: every tracked file gets an entry with `file`, `hash`, `hash-format`, an optional `metafile` bool, and an optional **`preserve`** bool. `metafile: false` marks an entry as a plain file (not a `.pw.toml` pointing at CurseForge/Modrinth) — i.e. it ships the literal bytes of whatever's in the pack folder. `preserve: true` on that entry tells packwiz-installer not to overwrite the file on a later update if it already exists locally — "preserving changes made by a user." That is precisely the property you want for `saves/<world>/`: ship it once on first install, then leave the player's own progress alone on every subsequent `packwiz refresh` push. *(Source: packwiz reference docs, index.toml page.)*

Caveats packwiz's docs do **not** resolve, and that matter at your world's likely size:
- A world folder is thousands of small region/entity/poi files, each of which becomes its own hashed `index.toml` entry unless you zip the world first and ship one file. Region files churn constantly (every chunk edit rewrites a `.mca`), so if you *do* want packwiz to track them individually, `preserve: true` per-file is mandatory or every player's world would get overwritten back to the shipped version on their next launcher update — that defeats the entire "second act changes the world" plan. Shipping the whole `saves/<name>/` as a **single pre-zipped file** (unzipped by a small pre-launch hook, one `preserve`-flagged entry) avoids the thousands-of-entries problem and is the more common real-world pattern.
- packwiz has no documented file-size cap of its own, but it serves files over plain HTTP from wherever `packwiz serve`/your host puts them — a multi-hundred-MB world zip is a bandwidth and first-install-time cost every player eats, and CurseForge/Modrinth pack export size limits (used if you ever mirror the pack there) are a separate, lower ceiling to check before committing to this path.
- **Confidence: high** on the `preserve`/`metafile` mechanism (official docs, fetched directly); **medium** on "zip it" being the practical answer for a world this size — that's inference from how the field works, not a documented packwiz world-shipping tutorial (no such tutorial page exists at `packwiz.infra.link`).

### 1b. Mod that installs a world template on first launch, instead of packwiz shipping the save

- **Serilum's Starter Structure** (CurseForge 2.2M+ downloads, GitHub `Serilum/Starter-Structure`, 1.20.1 available) is the most complete option: reads `.nbt`/`.schem`/`.schematic` files from `config/starterstructure/schematics/`, places one at spawn on world creation, and has real config depth — `forceExactSpawn`, `ignoreTreesDuringStructurePlacement` (skips leaves/logs so it doesn't plant your house in the canopy), `generationIgnoreJigsawAndStructureBlocks`, `protectStructureBlocks`/`protectSpawnedEntities`, per-axis position/offset overrides. This is a structure-placement mod, not a full-world-preset mod — it still generates normal terrain everywhere else and drops your build on top, same category of problem as the pack's own runtime `place_ruin.mcfunction`, just earlier (at world creation instead of at first join). Its README doesn't state dedicated-server support or terrain-adaptation behavior either way — untested by this pass. **Confidence: medium** — good docs on config, no verified answer on the exact "does it flatten or adapt" question that's the whole complaint.
- **Spawn Structures** (`Snugs/SpawnStructures_Forge`, CurseForge, 1.20.1) is a lighter alternative aimed at a starter-kit chest+bed, not a whole village. The author's own README says: *"there could be unforeseen bugs and I'm not currently 100% happy with the structure generation integration with the rest of the world,"* with "better structure generation integration with the world" listed as a roadmap item, not a shipped feature. **This is a direct admission of the exact symptom Josh described** ("doesn't feel like it's naturally on land") from the mod's own author — treat it as evidence *against* reaching for this mod for that specific goal. **Confidence: high** (direct quote from the source README).
- No mod named "Custom Starter Structure" turned up as a distinct project — likely a naming mix-up with Serilum's mod above, or with **Custom Default World Preset** (below), which is a different category (default *preset selection*, not structure placement).
- "Yet Another World Preset" does not appear to exist under that name for 1.20.1 Forge. The real mods in that space are **Default World Type** (MelanX, 10.4M downloads, 1.20.1 Forge/NeoForge — sets which world type/preset is *pre-selected* in the create-world screen, does not place any structure or content) and **Custom Default World Preset** (lets a datapack-defined world preset become the default) — neither ships or places a hand-built build; both are quality-of-life for the "New World" screen. **Confidence: high** that these are QoL-only, not structure-placement mods, based on their own descriptions.

### 1c. Dedicated-server side

A dedicated server just reads whatever folder `level-name` in `server.properties` points at (default `world`) — dropping a pre-built `world/` folder next to the server jar before first boot is the entire mechanism, no mod required. This is standard Minecraft server behavior, not something specific to this pack's mod list, and none of the sources above override it (a Forge/KubeJS mod placing structures at runtime still just edits chunks inside whatever `level-name` folder is already running). **Confidence: high** (basic, well-established server operation).

## 2. Placing the designed valley at world creation, not at runtime

### 2a. Starter-structure mods (repeat of 1b, same candidates)
Same three: Serilum Starter Structure, Spawn Structures, and (not found) "SpawnStructure"/"Custom Starter Structure" as separate projects. These place structures via their own placement code, **not** via vanilla structure-set worldgen — so vanilla's `terrain_adaptation` field (2c below) does not apply to them; whatever terrain handling they have is bespoke to the mod. Given Spawn Structures' own author says the terrain integration isn't there yet, and Serilum's docs don't confirm it either, **neither mod is a verified fix for "doesn't feel naturally on land"** — that property has to come from vanilla structure-set placement (which does have real terrain adaptation, see 2c) or from a bespoke terrain-matching pass in this pack's own KubeJS.

### 2b. Vanilla datapack structures "pinned to spawn" — the premise needs correcting
There is **no `spawn_override` field** in the vanilla `structure_set` schema. Fetched directly against the Minecraft Wiki's structure_set page, the full field list is: `structures`, `placement.type` (`minecraft:random_spread` or `minecraft:concentric_rings`), `salt`, `frequency`, `frequency_reduction_method`, `exclusion_zone`, `locate_offset`, and for random_spread specifically `spread_type`/`spacing`/`separation` (concentric_rings uses `distance`/`count`/`preferred_biomes`/`spread` instead). None of these guarantee a structure lands at or near the world's actual spawn point — the wiki is explicit that chunk (0,0) is only the *grid's counting origin* for `random_spread`, not a placement guarantee, and spawn-point selection itself is a separate, independent algorithm. **Confidence: high** — this is a corrected finding, not a confirmed one: if the plan is "pin the valley to spawn via a structure_set field," that field doesn't exist in vanilla, so it isn't a viable path as stated. The workable vanilla-only approximation is tuning `spacing`/`separation`/`salt` on a `random_spread` set so a piece is *very likely* to land within the guaranteed spawn-search radius — likely, not guaranteed — or leaning on a placement mod (2a) instead, accepting its terrain trade-offs.

- There is a separate, differently-named `spawn_overrides` field, but it lives on the **structure definition** (not the structure set) and only overrides which mobs are allowed to spawn inside the structure (e.g. why Ancient Cities suppress most mobs) — unrelated to world placement. Worth flagging so this name isn't confused with a placement mechanism in future planning.

### 2c. Structure size and terrain adaptation — the part that's actually usable
- A single structure-block/NBT template caps at **48×48×48**. Jigsaw structures exist specifically to get past that: a jigsaw structure assembles many ≤48³ pieces at generation time with no hard ceiling on the assembled whole — villages, pillager outposts, bastions, ancient cities, trail ruins and trial chambers are all jigsaw for exactly this reason. A whole-town design bigger than 48 blocks per axis (which this pack's town clearly is, per `town_plan.js`'s 26 build groups) needs the jigsaw system, or the pack's existing multi-`/place template`-call approach (functionally similar, just hand-orchestrated instead of engine-driven). **Confidence: high** (wiki, corroborated by two independent sources).
- `terrain_adaptation` on a structure definition is real and is the actual answer to "make it sit naturally instead of on a cut pad": `none` (default — no adaptation, which is what a raw `/place template` onto a flattened pad amounts to), `beard_thin` (grows terrain in under the structure while clearing terrain inside its footprint — used by pillager outposts and villages, i.e. the closest vanilla analogue to "a house standing on natural ground"), `beard_box` (an "advanced" beard_thin variant, ancient cities), `bury` (piles terrain around/over the structure — strongholds), `encapsulate` (an "advanced" bury variant — trial chambers). **This field only fires as part of vanilla jigsaw/structure worldgen** — it's not something you can invoke from a KubeJS `/place template` call or from the starter-structure mods above, because those bypass the structure-generation pipeline entirely. To get real terrain_adaptation behavior for the valley, the valley's ruin/cottage/town pieces would need to become an actual registered jigsaw structure (data-driven, `structure_set` + `structure` + template pool json, likely via a small Java/KubeJS-exposed registration or a datapack folder baked into the pack) rather than the current runtime `/place template` + manual pad-cutting. That is a real, larger engineering lift than swapping a mod in — worth flagging as the highest-leverage but highest-cost fix for "doesn't feel naturally on land." **Confidence: high** on what the field does; **medium** on the feasibility/cost estimate for retrofitting it onto this pack's runtime-generated valley, which is inference, not something a source stated directly.

## 3. Additive, gradual change instead of a runtime swap

### 3a. Schematicannon / Schematic Table without client upload
Per Create's own wiki (`Creators-of-Create/Create` wiki, "Loading a Schematic," fetched directly): schematics load from a `/schematics` folder into a **Schematic Table**, and "the schematic is being uploaded onto the server in order to be place-able by server side actors" — meaning the print/placement step is already server-authoritative once a schematic item exists; the player-facing "Upload" step is about getting the file's bytes onto the server, not about running the print. Nothing in Create's own docs, nor in a follow-up search for command/NBT-driven triggering, surfaced a documented command or KubeJS-exposed hook to hand a Schematicannon a schematic and start it printing with zero player interaction — the wiki's entire documented workflow is player-driven (place item → scroll to file → confirm → cannon). Create: Enhanced Schematicannon (a separate addon) improves *fidelity* of what gets captured server-side, not the automation/trigger question. **Confidence: medium-high that there is no documented headless trigger** — an absence-of-evidence finding after a real search, not a confirmed "impossible," since Create's block-entity NBT is technically writable by any mod/KubeJS with Java interop; it just isn't a supported or documented path.
- **Practical implication:** for a scripted "the town changes overnight," a custom KubeJS placer reading structure NBT directly (3b) is the supportable path, not driving a Schematicannon programmatically.

### 3b. Placement that preserves existing (player-placed) blocks
Vanilla's `/place template` has **no option to skip existing blocks** — its documented arguments are template, position, rotation, mirror, `integrity` (random *degradation*, not "skip occupied space"), `seed`, and `strict` (skip block/shape updates, not skip-if-occupied). Fetched directly from the Minecraft Wiki commands page. So the pack's existing pattern (cut pad → `/place template`, as in `place_ruin.mcfunction`) is structurally incapable of preserving anything a player added inside the footprint — this matches Josh's exact complaint ("the house gets fully replaced and everything that's there breaks"). The fix has to be a custom placer: KubeJS reading a structure's NBT tag list block-by-block and, for each intended-block position, checking the live world state first and skipping the write if that position doesn't match the "known baseline" (i.e., a player changed it) — which is exactly the "KubeJS block-by-block placer... can skip player-placed blocks" idea in the brief. This pack doesn't have one yet (no `StructureTemplate`/NBT-reading placer found anywhere in `pack/kubejs` or `server/kubejs`); it would be new code, not a config change. **Confidence: high** on the `/place template` gap (direct doc); **medium** on implementation shape, since no source documents this exact pattern for KubeJS 2001.6.5 — it's an inference from what the engine exposes plus what this pack has already proven it can do with per-tick JS logic.

### 3c. Stardew-style overnight change, triggered on sleep/dawn
This pack has **already solved the detection half of this problem**, and it's worth reusing rather than re-inventing: `valley_checks.js` (confirmed in-repo, lines ~507-521) documents that *"PlayerEvents has NO wakeUp/sleep event in KubeJS 2001.6.5 (verified against the jar)"* and instead polls `player.isSleeping()` every tick, tracking a per-player `sleeping[name]` boolean and firing only on the **sleeping → awake edge** (the "was asleep last tick, isn't now" transition) — which is the exact "at dawn" moment a Stardew-style change should land on. This is a first-party, engine-verified fact about this KubeJS build, not a general claim: **confidence: high** (it's this pack's own comment, stating it was checked against the actual jar). The 2-line follow-on this research didn't find prior art for but which fits directly on top of the existing pattern: gate a scheduled "overnight build" (the block-by-block placer from 3b) behind "all currently-online players just hit the sleeping→awake edge in the same tick window," so nothing changes while a player's eyes are open and nothing changes for a player who chose not to sleep.

### 3d. Nothing happens under the player's feet — timing, not just triggers
Given 3c is already proven, the remaining piece is purely sequencing: fire the change on the awake-edge tick (player's screen is mid-fade-in from sleep, a natural cover moment), not on a raw server-tick/day-count poll that could land while someone's mid-build. No source materially disagreed with this — it's a direct consequence of what 3a-3c already establish, not a separate researched claim.

## 4. Protecting the player's own blocks

- **FTB Chunks** is not in the pack (only FTB Library/Quests/Teams/XMod-Compat are). It's the standard claim-and-protect mod in the FTB family — claim chunks, ally players, "shift-click to toggle forceload." Its protection is **chunk-grained**, not block- or footprint-grained: claiming a chunk to protect one player-placed fence post also walls off everything else in that 16×16 column, including whatever the town-plan wants to build there later. A known compatibility note: Building Gadgets 2 has an issue where it bypasses FTB Chunks' claim protection on 1.20.1/NeoForge (tracked upstream, `Direwolf20-MC/BuildingGadgets2#230`) — a reminder that "protected" is mod-dependent, not universal. **Confidence: high** the mod does what's claimed; **medium** on whether chunk-grained protection is fine-grained enough for "protect just the things the player touched" — that's a fit judgment, not a documented limitation of the mod itself.
- The alternative already implied by 3b — a **footprint/baseline whitelist** inside the custom KubeJS placer (skip any position where live world state differs from the last-known baseline) — protects at block granularity and requires no additional mod, at the cost of being code you maintain rather than a mod you install. Given the pack already tracks persistent per-block state for lamps (`VALLEY.OFF`/lamp NBT logic in `valley_core.js`), the pattern for "remember what I placed vs. what the plan placed" already exists in spirit in this codebase. **Confidence: medium** (architectural inference from what's already in the pack, not a documented technique from any source).

## 5. Making the change feel like magic, not a swap

No single authoritative source for "how modpacks with strong storylines handle this" turned up a documented playbook — general web search for narrative-modpack world-transition design returned only *lists of story-flavored modpacks* (Story Edition, Eternal Tales, MineColonies, FTB Revelations, Forever Stranded), not design write-ups of *how* they handle the moment of change. That's a real gap in this research pass, not a saturated area — worth a follow-up search specifically against modpack changelogs/dev-blogs (e.g. MineColonies' own "how building upgrades render" docs) rather than general search, if this matters enough to spend more budget on. **Confidence: low** on this section specifically — it's synthesis from the mechanics already confirmed above (sleep-edge trigger, particles/sound/title being standard, universally-available Minecraft primitives), not from a "here's how Pack X does it" source.

What *is* directly supported by mechanics already confirmed above: firing the change on the sleeping→awake edge (3c) already buys the "you weren't watching" cover a magic-feeling reveal needs. Standard, unresearched-because-they're-vanilla-primitives options that combine with that timing: `/particle` bursts as each piece resolves, a `/title`/`/tellraw` cue at the wake moment, a sound cue via `/playsound`, and — if the block-by-block placer (3b) is staged rather than instant — spacing individual block placements over a few seconds so the reveal reads as a small "unfolding" rather than a single-tick pop. None of this required new research; it's existing Minecraft command surface the pack already uses elsewhere (e.g. `valley_core.js`'s lamp-lighting sequencing).

## 10 findings, ranked, with confidence

1. **(High)** packwiz's `index.toml` supports exactly the "ship a world once, never overwrite the player's changes again" need via `metafile: false` + `preserve: true` on a file entry — confirmed directly from packwiz's own docs. Practical caveat (medium confidence): ship the world as one pre-zipped `preserve`-flagged file, not thousands of individual `.mca` entries.
2. **(High)** Vanilla `structure_set` has no `spawn_override` field. The premise in the brief doesn't match the current schema (confirmed against the Minecraft Wiki's structure_set page) — pinning a structure to spawn via vanilla worldgen means tuning `random_spread` spacing/separation/salt for high *likelihood*, not a guarantee, or accepting a placement mod's own (non-worldgen) spawn logic instead.
3. **(High)** `terrain_adaptation` (`beard_thin`/`beard_box`/`bury`/`encapsulate`) is real and is the actual vanilla mechanism for "sits naturally on land instead of on a cut pad" — but it only fires inside real jigsaw/structure-set worldgen, not from a `/place template` call or from any of the starter-structure mods checked. Getting it for this valley means registering the valley as an actual jigsaw structure, which is a real engineering project, not a mod install (medium confidence on cost/feasibility, high on the mechanism itself).
4. **(High)** Spawn Structures' own author states in the mod's README that terrain integration "isn't 100% happy" yet, with better integration only on the roadmap — direct evidence that this specific mod does not currently solve the "doesn't feel natural on land" complaint. Serilum's Starter Structure doesn't confirm the answer either way in its docs.
5. **(High)** A single structure template caps at 48×48×48; jigsaw is the only way past that for a build the size of this pack's town (26 build groups per `town_plan.js`). This pack's current multi-`/place template`-call approach is a manual workaround for the same limit jigsaw solves natively.
6. **(High)** `/place template` has no "skip existing/player blocks" option (confirmed against the wiki's command reference) — this is the direct, confirmed cause of "the house gets fully replaced and everything that's there breaks." Fixing it requires a custom block-by-block placer, not a command flag.
7. **(High)** This pack has *already* solved sleep detection: `valley_checks.js` polls `player.isSleeping()` per tick and fires on the sleeping→awake edge, because KubeJS 2001.6.5 has no sleep/wake event (verified by this pack's own devs against the jar). This is the correct, already-proven hook to gate any future "overnight change" on — no new detection code needed, only a new action to attach to the existing edge.
8. **(Medium-high)** No documented way exists to drive a Create Schematicannon to load and print a schematic without player interaction (checked Create's own wiki + a follow-up search); the supportable path for scripted world change is a custom KubeJS structure-NBT placer, which also solves finding 6.
9. **(Medium)** FTB Chunks (not currently installed) protects at chunk granularity, not block/footprint granularity, and has at least one documented mod-compat bypass (Building Gadgets 2). A baseline-whitelist inside a custom placer (skip any position that no longer matches the last-known plan state) protects at the granularity Josh actually needs, reusing this pack's existing persistent-state patterns, at the cost of being bespoke code rather than an installed mod.
10. **(Low)** No source-backed playbook was found for how narrative-driven modpacks specifically stage world-change "reveals" — general search only surfaced lists of story-flavored packs, not design write-ups. The "make it feel like magic" recommendations here (particle/sound/title cues timed to the sleep-wake edge, staged rather than instant placement) are synthesis from the vanilla primitives already confirmed above, not a documented pattern from another pack. Worth a targeted follow-up (e.g. MineColonies dev docs) if this axis matters enough to spend more research budget on.
